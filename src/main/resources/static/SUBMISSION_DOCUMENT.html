1. Introduction

BudgetBuddy AI is an end-to-end autonomous transaction categorization system that uses machine learning to intelligently classify financial transactions into user-defined categories. Built with a production-ready architecture, the system eliminates third-party API dependencies while achieving high accuracy through advanced deep learning techniques.

The system transforms raw transaction strings (UPI narrations, bank descriptions) into structured categories using a fine-tuned DistilBERT multi-task model. Beyond categorization, BudgetBuddy provides spending analytics—detecting patterns, analyzing trends, and generating insights to help users understand their transaction data.

Key Highlights

100% Private

All data processing happens locally on your device. No cloud dependencies, no data sharing.

High Accuracy

3. Data Model & Storage

Data Strategy & Dataset

The system uses a carefully curated dataset for training and evaluation:

  • Dataset Source: The training dataset consists of real-world financial transaction data collected from various sources, including UPI transaction narrations, bank statement descriptions, and manually labeled transaction strings. The dataset represents diverse transaction patterns across multiple categories.
  • Dataset Composition: 3,712 training samples, 928 test samples (80/20 split), with 10% validation set for early stopping
  • Data Preprocessing:
    • Transaction strings are cleaned to remove UPI tags, transaction IDs, and special characters
    • Text normalization: lowercase conversion, whitespace standardization
    • Tokenization using DistilBERT tokenizer with max length of 128 tokens
    • Handling of noisy inputs: special characters, abbreviations, and variations in merchant names
  • Data Quality & Robustness:
    • Dataset includes diverse transaction formats: "UPI/PAYTM/123456", "Amazon.com", "Shell Gas Station", etc.
    • Handles variations in merchant naming conventions and abbreviations
    • Robust to input noise through preprocessing pipeline and model generalization
    • Category consolidation strategy addressed class imbalance (reduced from 64 to 26 categories)
  • Reproducibility: The dataset and preprocessing pipeline are documented in the codebase. Training scripts include seed setting for reproducibility, and all data splits are deterministic.

Database Schema

Core Entities

Transaction

  • Primary Key: id (Long)
  • Attributes: date, narration, amount, withdrawalAmt, depositAmt, closingBalance

  • Primary Key: id (Long)

  • Primary Key: id (Long)

  • Transaction Data: All transactions with ML predictions stored
  • Spending Analytics: Pre-calculated insights stored for fast retrieval

4. AI / ML / Automation Components

Machine Learning Model

Model Architecture

BudgetBuddy AI employs a sophisticated multi-task learning architecture based on DistilBERT, a lightweight variant of BERT that maintains high performance while reducing computational requirements. The model architecture consists of:

  • Base Model: DistilBERT (distilbert-base-uncased) - A distilled version of BERT with 66 million parameters (compared to BERT's 110 million), providing 60% faster inference while retaining 97% of BERT's performance
  • Type: Multi-task learning model that simultaneously learns three related tasks, enabling knowledge sharing and improved generalization
  • Tasks:
    • Transaction Type Classification: Predicts whether a transaction is P2C (Person-to-Consumer), P2P (Person-to-Person), or P2Business. This classification helps understand the nature of the transaction and improves category prediction accuracy
    • Category Classification: Predicts one of 26 consolidated categories (optimized from 64 to reduce class imbalance)
    • Intent Classification: Identifies the intent behind the transaction: purchase, transfer, refund, subscription, bill_payment, or other. This provides additional context for spending analytics

The multi-task learning approach allows the model to learn shared representations across tasks, improving performance on each individual task compared to training separate models.

Model Performance

Performance Metrics: Macro F1-Score: 0.8961 (89.61%), Weighted F1-Score: 0.9010 (90.10%) - exceeding the 0.90 performance target. Training on 3,712 samples, testing on 928 samples. 26 consolidated categories (optimized from 64). The weighted F1-score of 0.9010 demonstrates that the model achieves the required 90%+ accuracy threshold for production use.

Evaluation Report

The training pipeline generates comprehensive metrics saved to reports/distilbert_metrics_[timestamp].json, including confusion matrices, per-class F1 scores, and classification reports for all tasks. Evaluation uses stratified 80/20 train-test split with 10% validation set for early stopping.

Model Training Process

The training pipeline is designed for reproducibility and continuous improvement:

  • Framework: PyTorch with Hugging Face Transformers library, providing state-of-the-art transformer implementations
  • Training Script: train_distilbert.py - A comprehensive training script that handles data loading, preprocessing, model initialization, training loop, and evaluation
  • Training Configuration:
    • Epochs: 8 epochs (optimized through experimentation to balance training time and performance)
    • Batch Size: 16 samples per batch, optimized for available GPU memory
    • Learning Rate: 2e-5 with linear warmup over 500 steps, followed by cosine decay
    • Optimizer: AdamW with weight decay of 0.01
  • Class Weights: Applied inverse frequency weighting to address class imbalance, ensuring the model learns from underrepresented categories
  • Hyperparameters: Optimized through grid search and validation set performance, including learning rate, warmup steps, and dropout rates
  • User Corrections: Automatically included in training pipeline through add_correction.py script, enabling continuous learning from user feedback
  • Validation Strategy: 10% of training data held out for validation, with early stopping based on validation F1-score to prevent overfitting

Inference Pipeline

Priority-Based Categorization System

The system employs a sophisticated three-tier priority-based categorization approach that combines rule-based matching with machine learning predictions:

  1. User Corrections (Highest Priority - 100% Confidence)
    • Source: user_corrections.json file containing preprocessed narrations and their user-assigned categories
    • Confidence Level: 100% - User corrections are treated as ground truth
    • Storage: In-memory cache (HashMap) for O(1) lookup performance, with database persistence for durability
    • Preprocessing: Corrections are stored with preprocessed narrations (cleaned of UPI tags, IDs) to ensure exact matching
    • Persistence: Corrections are also stored in the category_keyword table with categoriesFor = "Corrected" for database queries
    • Performance: Sub-millisecond lookup time for cached corrections, enabling real-time categorization
  2. Taxonomy Keywords (Rule-Based Matching - High Confidence)
    • Source: categories.yml YAML file containing 707+ keywords mapped to categories, automatically loaded into database on application startup
    • Matching Algorithm: Word-boundary matching using regex to ensure keywords match complete words, not substrings
    • Priority Strategy: Longest keyword first - when multiple keywords match, the longest keyword takes precedence for more specific categorization
    • Coverage: 707+ keywords across 26 categories, providing comprehensive coverage for common transaction patterns
    • Performance: Fast database lookup with indexed queries, typically <10ms per transaction
    • Maintenance: Keywords can be added or modified in YAML file without code changes, enabling easy taxonomy updates
  3. DistilBERT Model (ML Prediction - Variable Confidence)
    • Multi-task Predictions: Simultaneously predicts category, transaction type, and intent in a single forward pass
    • Confidence Scores: Provides probability distributions (0.0 to 1.0) for all predictions, enabling uncertainty quantification
    • Batch Processing: Processes multiple transactions in a single inference call, significantly improving throughput
    • Subcategory Extraction: Automatically extracts subcategories from category predictions when applicable
    • Fallback Mechanism: Used when user corrections and keyword matching fail, ensuring all transactions receive a category
    • Performance: ~50-100ms per transaction (single), ~500ms for 100 transactions (batch)

Customizability & Taxonomy Management

The system is designed for maximum customizability without requiring code changes:

  • YAML-Based Taxonomy Configuration:
    • All category keywords are defined in categories.yml file, enabling admin-driven updates
    • Categories and keywords can be added, modified, or removed by editing the YAML file
    • Changes take effect on application restart without requiring code deployment
    • YAML format is human-readable and easy to maintain
  • Dynamic Category Management:
    • New categories can be added to the taxonomy by updating the YAML configuration
    • Category consolidation and splitting can be managed through configuration changes
    • Model can be retrained with updated taxonomy when categories change significantly
  • User-Driven Corrections: Automatically integrated into pipeline, stored in user_corrections.json and database, exportable for retraining
  • Configuration-Driven: ML confidence thresholds, batch sizes, and analytics parameters configurable

Text Preprocessing Pipeline

The preprocessing pipeline is critical for model performance, as it normalizes transaction narrations while preserving semantic meaning:

  • UPI Prefix Removal: Removes common UPI prefixes like UPI-, UPI/, UPI to normalize transaction descriptions
  • Bank Tag Removal: Strips bank identifiers such as @YBL, @HDFCBANK, @PAYTM that don't contribute to categorization
  • Transaction ID Removal: Identifies and removes long numeric sequences (typically 10+ digits) that represent transaction IDs
  • Separator Normalization: Standardizes various separators (hyphens, slashes, spaces) to consistent formats
  • Semantic Preservation: Carefully designed to preserve merchant names, locations, and transaction context
  • Centralized Implementation: All preprocessing logic is centralized in the NarrationPreprocessor utility class, ensuring consistency across web and mobile applications
  • Preprocessing for Corrections: User corrections are stored with preprocessed narrations to ensure exact matching during inference

Batch Processing Optimization

The batch processing system provides significant performance improvements:

  • Single Model Load: Model is loaded once per batch, eliminating repeated initialization overhead
  • Vectorized Operations: PyTorch's batch processing enables vectorized operations across multiple transactions
  • Performance Gains: 10-100x faster than sequential processing, with diminishing returns after ~100 transactions per batch
  • Memory Management: Batch size is dynamically adjusted based on available memory and transaction count
  • Error Handling: Partial batch failures are handled gracefully, with successful predictions returned even if some transactions fail
  • Scalability: Can efficiently handle 1000+ transactions in a single batch import operation

Automation Components

Spending Analytics Automation System

The spending analytics system provides comprehensive automated insights through an event-driven architecture:

  • Event-Driven Updates: The system uses Spring's event mechanism to automatically recalculate spending analytics whenever transactions are created, updated, or deleted. This ensures analytics are always current without manual refresh
  • Debouncing Mechanism: A 30-second debounce window batches multiple transaction changes, preventing excessive recalculations during bulk imports. This significantly improves performance during CSV uploads
  • Async Processing: All spending analytics calculations run asynchronously using Spring's @Async annotation, ensuring the user interface remains responsive during computation
  • Comprehensive Analytics: The system provides 10+ distinct analytics features:
    • Top 3 Spending Areas: Identifies the three categories with highest spending, excluding investments, providing quick insights into spending patterns
    • Category Overspending Alerts: Compares current month spending against historical averages (last 6 months) and flags categories with significant increases. Alert levels (LOW, MEDIUM, HIGH, CRITICAL) are based on percentage increase and statistical significance
    • Weekend Overspending Analysis: Analyzes spending patterns on weekends (Saturday-Sunday) versus weekdays, identifying categories with higher weekend spending
    • Year-End Savings Projection: Projects year-end savings based on current spending rate, providing best-case, likely, and worst-case scenarios including investment returns
    • Regular Monthly Spending Detection: Identifies recurring expenses that occur 3+ months consecutively, separating them from one-time expenses for better anomaly detection
    • Grocery vs Eating-Out Comparison: Compares grocery store spending versus restaurant/dining expenses, helping users understand food spending patterns
    • Investment Tracking: Separately tracks investment transactions, excluding them from expense calculations and providing cumulative investment totals
    • Subscriptions Analysis: Identifies recurring subscription payments (non-investment), helping users track subscription costs
    • Category Trend Visualization: Generates JSON data for 6-month spending trends by category, enabling chart visualization
    • ML-based Anomaly Detection: Uses Isolation Forest algorithm to identify unusual spending patterns that don't match regular monthly spending

Continuous Learning Framework

User corrections stored in user_corrections.json are automatically integrated into the inference pipeline with highest priority. Corrections can be exported for model retraining, creating a feedback loop that improves predictions over time.

ML-Based Anomaly Detection

The anomaly detection system uses advanced machine learning techniques:

  • Algorithm: Isolation Forest from scikit-learn, an ensemble method that identifies anomalies by isolating them in feature space
  • Purpose: Identifies unusual spending patterns that deviate from normal behavior, helping users identify errors or unexpected expenses
  • Feature Engineering: Uses transaction amount, category, day of week, and time since last similar transaction as features
  • Filtering Strategy: Excludes regular monthly spending patterns (identified through pattern detection) to focus on truly unusual transactions
  • Output Format: Provides unusual transactions with intent classification, confidence scores, and links to view transaction details
  • Performance: Runs asynchronously with manual trigger button to avoid blocking the UI during computation

5. Security & Compliance

Data Privacy

100% local processing with no external APIs. All data remains on-device/server. Mobile app works completely offline.

Data Security

  • Password Encryption: User passwords stored securely (Spring Security)
  • Database Security: MySQL with proper access controls
  • Input Validation: All user inputs validated before processing
  • SQL Injection Prevention: JPA/Hibernate parameterized queries
  • XSS Protection: Thymeleaf automatic escaping

Compliance Considerations

  • Data Minimization: Only necessary transaction data stored
  • User Control: Users can delete all their data
  • Transparency: Clear indication of ML predictions vs user corrections
  • Explainability: Confidence scores and prediction reasons provided
  • Bias Mitigation: Class weights and balanced training data

Responsible AI & Robustness

Bias Mitigation: Inverse frequency class weights address class imbalance. Category consolidation (64→26) improves representation. Model focuses on text patterns, not merchant/region/amount, ensuring fair categorization. Per-class F1-scores monitored for bias detection.

Robustness: Text preprocessing removes UPI tags, IDs, and special characters. Handles merchant name variations and formatting inconsistencies. Multi-tier categorization (user corrections → keywords → ML) with graceful error handling and fallback mechanisms.

Explainability: Each prediction includes reason and confidence score (0.0-1.0). Low-confidence predictions flagged for review. Taxonomy keywords visible in YAML configuration files.
